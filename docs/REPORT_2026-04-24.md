# CattleEval Project Work Report

**Date:** April 24, 2026

## Executive Summary

CattleEval is a full-stack mobile system for cattle species detection. The project is organized into three cooperating services: a React Native mobile app, a Node.js backend API, and a FastAPI machine learning inference service. The current implementation supports user registration and login, authenticated image upload, species prediction for cow vs buffalo, result persistence, and basic profile/settings management.

This report documents the work completed so far in the repository, based on the current codebase and packaged model artifacts. It explains how the mobile frontend, backend, and ML service are wired together, and it records the current state of the training assets that are available in the project.

## 1. Project Overview

The application is designed to help a user capture or upload a livestock image and receive an automated species classification result. The architecture is intentionally split into three layers so that each part of the system has a focused responsibility:

- The mobile application provides the user interface, image capture, authentication flow, and result display.
- The backend handles user accounts, session token validation, request forwarding, and evaluation persistence.
- The ML service loads the trained model and performs image preprocessing and inference.

The overall flow is:

1. The user creates an account or logs in through the mobile app.
2. The app stores a JWT token locally and uses it for authenticated requests.
3. The user selects or captures a body image.
4. The mobile app uploads the image to the backend.
5. The backend forwards the image to the ML service.
6. The ML service preprocesses the image and returns a species prediction with confidence.
7. The backend stores the prediction in MongoDB and returns the result to the app.
8. The mobile app displays the species, confidence, and timestamp.

## 3. System Architecture

### 3.1 Service Separation

The project is split into three services for clarity and maintainability.

#### Mobile app

The mobile app is an Expo Router application built with React Native. It is responsible for navigation, authentication screens, image capture, result presentation, and profile/settings access.

#### Backend API

The backend is an Express server connected to MongoDB with Mongoose. It exposes auth endpoints and an evaluation endpoint. It also acts as a bridge between the mobile app and the ML service.

#### ML inference service

The ML service is a FastAPI application that loads a saved TensorFlow/Keras model and exposes a `/predict` endpoint for image classification.

### 3.2 Data Flow

The system uses a straightforward request chain:

```text
Mobile App -> Backend API -> ML Service -> Backend API -> MongoDB -> Mobile App
```

This separation keeps the model inference logic isolated from session handling and UI concerns. It also makes the machine learning component independently testable.

## 4. Machine Learning Model Report

### 4.1 Available Model Artifacts

The repository includes the trained model files under `ml-service/model/`:

- `SpecieDetector.keras`
- `SpecieDetector.weights.h5`

The model archive contains a Keras configuration and weights, which can be loaded by the ML service at startup. The archive inspection shows the model is a binary classifier with the following structure:

- Input shape: `224 x 224 x 3`
- Feature extractor: `MobileNetV2` feature-vector layer from TensorFlow Hub
- Output layer: Dense layer with `2` units and `softmax` activation

That means the model is designed to classify an input image into one of two species classes. In the current application, those classes are mapped to `Cow` and `Buffalo`.

### 4.2 Inference Pipeline

The inference flow in `ml-service/main.py` is as follows:

1. Accept an uploaded image as multipart form data.
2. Read the file bytes into memory.
3. Decode the bytes into an OpenCV image.
4. Convert from BGR to RGB.
5. Resize the image to `224 x 224`.
6. Normalize pixel values to the `0-1` range.
7. Reshape the image to batch format `(1, 224, 224, 3)`.
8. Run model prediction.
9. Take the argmax of the output logits.
10. Map class `0` to `Cow` and class `1` to `Buffalo`.
11. Return species and confidence as JSON.

### 4.3 Model Loading Strategy

The service first attempts to load the model using `tf_keras.models.load_model(...)` with `hub.KerasLayer` supplied as a custom object. This is the normal path for a saved Keras model.

There is also a fallback loader for `.keras` archives. That fallback reconstructs the model structure from the archive metadata, restores the TensorFlow Hub feature-vector layer, and then loads the stored weights manually. This is useful when the saved model format needs special handling for bundled Keras/TensorFlow Hub components.

### 4.4 Methodology Used in the ML Service

The methodology implemented by the ML service is a practical transfer-learning inference approach:

- Use a pretrained MobileNetV2 feature extractor rather than training a CNN from scratch.
- Keep the feature extractor frozen at inference time.
- Train or fine-tune a small classification head for the two species classes.
- Standardize every image to the same input size and normalization range before inference.
- Return a confidence score alongside the predicted class so the UI can present both the label and the certainty.

This is a good fit for mobile-friendly image classification because MobileNetV2 is lightweight, fast, and suitable for embedded or near-real-time prediction pipelines.

### 4.5 Dataset and Notebook Status

The repository currently does not include the original training notebook or the dataset used to train the model. Because of that, the report cannot truthfully name the exact dataset source, split sizes, augmentation policy, or training hyperparameters from the source files alone.

What can be stated from the available artifacts is:

- The feature extractor is MobileNetV2 from TensorFlow Hub.

### 4.6 ML Service API

The ML service exposes two endpoints:

- `GET /` returns a simple health message.
- `POST /predict` accepts an uploaded image file named `bodyImage` and returns the predicted species and confidence.

The service also enables permissive CORS so it can be called from local frontend development environments.

## 5. Backend Report

### 5.1 Backend Role

The backend is the application’s control layer. It manages identity, authorization, request validation, evaluation storage, and communication with the ML service.

### 5.2 Technologies Used

The backend package uses:

- `express` for HTTP routing and middleware
- `mongoose` for MongoDB data modeling
- `jsonwebtoken` for JWT-based authentication
- `bcryptjs` for password hashing and verification
- `multer` for multipart file upload handling
- `axios` and `form-data` for forwarding images to the ML service
- `cors` and `dotenv` for environment and cross-origin configuration

### 5.3 Server Setup

The server entry point connects to MongoDB, enables JSON parsing and CORS, mounts the route groups, and includes a centralized error handler. The backend serves a simple root health response and registers the auth and evaluation route groups under `/api/auth` and `/api/evaluate`.

### 5.4 Authentication Flow

The auth controller supports:

- User registration
- User login
- Profile retrieval
- Settings updates
- Logout acknowledgement

Registration validates required fields, checks for duplicate emails, hashes the password, creates the user, and returns a signed JWT token.

Login validates the submitted credentials against the stored hash and returns a JWT token on success.

The middleware verifies `Bearer` tokens on protected routes, decodes the token, and attaches the user ID to the request object.

### 5.5 Evaluation Flow

The evaluation endpoint is protected by authentication and accepts a single uploaded image field called `bodyImage`.

The controller then:

1. Validates that an image file was included.
2. Builds a multipart form payload.
3. Forwards the image to the ML service `/predict` endpoint.
4. Reads back the species and confidence.
5. Stores the result in MongoDB.
6. Returns the prediction data and creation timestamp to the caller.

This design lets the backend act as a secure middleware layer between the mobile client and the ML inference service.

### 5.6 Database Models

The backend includes at least two Mongoose models:

- `User` for account data and preferences
- `Evaluation` for prediction history

The evaluation schema stores:

- `userId`
- `bodyImage`
- `result.species`
- `result.confidence`
- `createdAt`

This structure supports future history views or analytics without changing the inference service.

### 5.7 Backend API Summary

The current API surface includes:

- `POST /api/auth/register`
- `POST /api/auth/login`
- `GET /api/auth/profile`
- `PUT /api/auth/settings`
- `POST /api/auth/logout`
- `POST /api/evaluate`

The evaluation endpoint is the main bridge between the app and the model.

## 6. Frontend Report

### 6.1 Frontend Role

The frontend is built as an Expo mobile application and provides the user-facing experience for authentication, image submission, result review, and account settings.

### 6.2 Navigation Structure

The app uses Expo Router with a stack-based layout. The root layout hides the native header and lets the app manage its own screen design.

The startup screen checks for a stored token in local storage and redirects the user either to the hero landing page or directly into the authenticated home flow.

### 6.3 Main Screens

#### Hero screen

The hero screen acts as the public landing page. It introduces the product, presents the high-level value proposition, and routes users to login or additional information.

#### Login and register screens

These screens collect user credentials, call the backend authentication endpoints, store the returned token in AsyncStorage, and move the user into the authenticated area.

#### Home screen

The home screen is the core operational screen. It allows the user to select or capture an image, submit it for analysis, and open the side menu for navigation.

#### Result screen

The result screen displays the predicted species, confidence, and timestamp. It also includes a button to start a new evaluation.

#### Profile screen

This screen loads the authenticated user profile and displays account details.

#### Settings screen

This screen allows the user to update the preferred language and toggle alert settings.

#### About screen

The repository also includes an about page for project information and team context.

### 6.4 Shared Components

The frontend reuses a small set of components to keep the screens consistent:

- `ImagePicker` handles camera and gallery selection.
- `ResultCard` formats the prediction output.
- `AppSidebar` provides the shared menu used across authenticated screens.
- `BackgroundWrapper` supplies a consistent background treatment on the auth screens.

### 6.5 Client API Integration

The mobile service wrapper centralizes all backend requests.

It handles:

- register
- login
- evaluation submission
- profile retrieval
- settings saving
- logout

An Axios interceptor attaches the JWT token from AsyncStorage to every request when available. This keeps the authentication logic out of each individual screen.

### 6.6 Image Capture and Upload UX

The `ImagePicker` component requests both camera and media library permissions, then lets the user either:

- choose a photo from the gallery
- capture a new photo with the camera

The selected image is previewed before submission, which improves usability and reduces bad uploads.

### 6.7 Result Presentation

The `ResultCard` component displays the prediction in a compact, readable format. It converts the species into a simple visual cue using an emoji and formats the confidence and timestamp for the user.

## 7. Implementation Methodology

The project follows a layered methodology rather than a monolithic one.

### 7.1 Backend-as-Orchestrator Pattern

The backend is used as the orchestrator for authenticated evaluation requests. This is helpful because it centralizes token validation, request logging, model forwarding, and persistence.

### 7.2 Stateless Inference Service

The ML service remains stateless. It does not manage users or sessions. It only loads the model, preprocesses the image, and returns the classification. This makes the inference layer easier to scale and easier to replace later.

### 7.3 Mobile-First Workflow

The frontend is optimized around a simple mobile-first flow:

1. Authenticate.
2. Capture or upload an image.
3. Review the result.
4. Repeat or inspect profile/settings.

This keeps the user path short and practical for field usage.
